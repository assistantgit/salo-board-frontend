# Архітектурні правила та Code Style (Фронтенд)

Цей файл містить ключові правила для ШІ та розробників при створенні або рефакторингу коду в проекті. Дотримання цих правил гарантує підтримання архітектури Feature-Sliced Design, принципів SOLID, а також консистентності CSS-системи.

## 1. Архітектурний підхід: Feature-Sliced Design (FSD)
Проект суворо дотримується архітектури FSD (Feature-Sliced Design).
- **app**: Глобальні налаштування, провайдери, глобальні стилі (`globals.css`), роутер.
- **pages**: Композиція віджетів і фіч у повноцінні сторінки. Відображення без складної бізнес-логіки.
- **widgets**: Самостійні блоки інтерфейсу (наприклад, Header, LoginForm). Вони можуть об'єднувати сутності та фічі.
- **features**: Самостійні фрагменти бізнес-логіки / взаємодії (кнопка Logout зі своїм API, перемикач теми). Увага: feature виконує тільки *одну* конкретну дію (Single Responsibility).
- **entities**: Бізнес-сутності та їх логіка (наприклад, UserAvatar, UserStore).
- **shared**: Інфраструктура, базові UI-компоненти (кнопки, інпути, модалки), API клієнт, утиліти. Не має жодних залежностей від інших шарів.

**Ключове правило напрямку залежностей:** шари можуть імпортувати код ТІЛЬКИ з нижестоящих шарів (`pages` -> `widgets` -> `features` -> `entities` -> `shared`). Ніколи не навпаки!

## 2. CSS-архітектура та Стилізація (ОНОВЛЕНО)

Ми відмовилися від глобальної "помийної ями" змінних. Суворий розподіл зон відповідальності.

### 2.1. Глобальні стилі (`globals.css`)
- Містять **тільки інфраструктурні токени**: глобальні шрифти (`--font-main`, `--font-secondary`), базові радіуси (`--radius-full`), переходи.
- Містять загальні CSS-resets та стилізацію `body`.
- **ЗАБОРОНА:** В жодному разі не додавати жодних глобальних змінних кольорів (ні `--main-bg-color`, ні `--text-color-1`) у `globals.css`.

### 2.2. Локальні/Компонентні змінні `/* ── Color tokens ── */`
Всі кольори повинні декларуватися локально всередині `.css` або `.module.css` конкретного компонента.
1. Структура: Оголошуємо змінні в селекторі-контейнері (найвищий батьківський клас).
2. Неймінг: Використовуємо **семантичні назви для конкретної сутності** (наприклад: `--card-bg`, `--input-border-focus`, `--submit-bg`). Уникаємо універсальних числових суфіксів.
3. Формат: Значенням має бути конретний колір (HEX або `rgba`).

Приклад:
```css
.login-card {
  /* ── Color tokens ── */
  --card-bg: #ffffff;
  --card-border: #E8E8EE;
  
  background-color: var(--card-bg);
  border: 1px solid var(--card-border);
}
```

### 2.3. Dark Mode (Темна тема)
Варіації для темної теми повинні перевизначатися **в тому ж самому файлі**, де оголошено локальні змінні, використовуючи глобальний селектор `html[data-theme='dark']`.
Це робить код модульним (стилі не розкидані по різних файлах).

Приклад:
```css
html[data-theme='dark'] .login-card {
  --card-bg: #1c1c38;
  --card-border: rgba(101, 96, 224, 0.25);
}
```

### 2.4. Респонсивність (Responsive Design)
- Уникати фіксованих розмірів у `px` там, де компонент має підлаштовуватися.
- Надавати перевагу сучасній функції **`clamp()`** для шрифтів, відступів (padding/margin), ширини та висоти вікон, щоб забезпечити плавне масштабування між мобільними та десктопом (fluid design).
- Робити відступи (padding) за допомогою `rem` та `em` там, де доцільно.
- Використовувати `@media` запити (в основному `(max-width: 768px)` та `(max-width: 480px)`) тільки тоді, коли потрібна структурна зміна макета (наприклад, `flex-direction: column` або приховання елементів).

### 2.5. Анімації та мікроінтеракції
Дизайн повинен бути преміальним та "відчуватися живим":
- Кожна інтерактивна кнопка (`button`) або посилання (`a`) має містити стани `:hover` та `:active`. 
- Стан `:hover` — зазвичай супроводжується зміною кольору/тіні та незначним збільшенням `transform: scale(1.05)`.
- Стан `:active` — зазвичай просідає або зменшується `transform: scale(0.95); transition: transform 0.1s;`.
- Використовувати `will-change` для оптимізації важких анімацій (напр. зсуви або transform).
- Форми (зокрема `LoginForm`, `RegisterForm`) використовують анімації для помилок (наприклад, `@keyframes formShake` або `fieldErrorSlideIn`).

## 3. SOLID принципи в дії
- **Single Responsibility Principle (SRP):** Один компонент — одна відповідальність. Наприклад, `LogoutButton` відповідає тільки за кнопку та її API-запит виходу, не варто тягнути туди логіку автентифікації користувача.
- Замість створення "God Components", розбивайте їх на дрібні, незалежні Shared UI компоненти і компонуйте їх в Widgets.

## 4. Стек і формати
- **CSS:** Vanilla CSS (CSS Modules `*.module.css` або звичайний scoping через унікальні назви класів).
- **Icon System:** Всі іконки імпортуються з `@shared/lib` (через `createIcon`).
- **Синтаксис:** Strict TypeScript (`.tsx`). Уникати використання типу `any`. Типізація через інтерфейси над компонентом (`interface ComponentProps { ... }`).
